# 🏚️ Zakkend Nederland

> **ML-powered foundation subsidence risk assessment for Dutch homes.**
> An estimated **1 million Dutch homes** face foundation damage from soil subsidence,
> with total damage projected at **€60+ billion by 2050**. Homeowners currently have
> no way to know their risk until cracks appear. This project changes that.

## The problem

Peat soils shrink in drought. Wooden pile foundations rot when groundwater drops.
Together, these phenomena cause slow, irreversible foundation damage across the
western Netherlands — especially in cities built on reclaimed land (Gouda, Rotterdam-Zuid,
Zaanstad, Amsterdam-Noord, Dordrecht).

Key facts that make this a real problem worth solving:

- **1,000,000+** Dutch homes at risk (KCAF, TNO estimates)
- **€60B+** projected repair cost by 2050
- **Insurers do not cover** subsidence damage
- **Mortgage banks** (ING, Rabobank, ABN AMRO) are scrambling for risk models
- **Municipalities** need prioritization tools for funding schemes
- **Homeowners** have no accessible tool to check their own address

## Labels and metrics

There is no public per-address ground truth for Dutch foundation damage. The labels
used here — `low`, `moderate`, `high`, `critical` — are generated by an explicit,
documented rule engine in `synthetic._compute_risk_score`: a weighted sum of the 11
input features, plus a small noise term, thresholded at three fixed cutoffs.

This means the reported accuracy measures **rule-recovery** — how well XGBoost
reconstructs the rule engine's output — not real-world predictive skill. The 17%
gap from perfect is almost entirely the noise term straddling the thresholds; on a
noiseless version of the labels the model would score ~99%.

This is a legitimate use case: it proves the feature engineering pipeline and training
loop are wired correctly end-to-end. But it is a **pipeline integrity check**, not
evidence that the model can predict actual foundation damage. The next milestone
toward real predictive value is weak supervision from KCAF/municipal *funderingsrisico*
zone data; see `docs/LIMITATIONS.md`.

> The metrics in this README come from a **synthetic, 10,000-row training run**
> (8,000 train / 2,000 test), regenerated at the categorical-encoding fix commit
> on the `hardening` branch. They do not reflect a real-data run.

## Data sources

Of the 11 model features, only 1 is measured directly from a government registry.
`building_age` is arithmetic (`2026 − year_built`, computed in `pipeline._harmonize_to_schema`)
— it carries no additional information beyond `year_built` itself and is not a
separate real measurement:

| Feature | Source |
|---------|--------|
| `year_built` | ✅ PDOK BAG `bouwjaar` (measured) |
| `building_age` | ↳ Arithmetic derivative of `year_built` (`2026 − year_built`) |
| `soil_type` | ⚠️ Coordinate-based rule engine; PDOK BRO WFS API exists but is disabled by default (`use_soil_api=False`) |
| `peat_thickness_m` | ❌ `np.random.default_rng` seeded by coordinates, priors from TNO thickness ranges |
| `groundwater_depth_m` | ❌ `np.random.default_rng(42)`, draws from soil-type normal distributions |
| `groundwater_variability` | ❌ `np.random.default_rng(42)`, draws from soil-type beta distributions |
| `insar_deformation_mm_yr` | ❌ `np.random.default_rng` seeded by coordinates, mean values informed by BodemDalingsKaart published rates |
| `drought_exposure_index` | ❌ `np.random.default_rng` seeded by coordinates, latitude gradient from KNMI spatial maps |
| `distance_to_water_m` | ❌ `np.random.default_rng(42)`, exponential draw with east/west split |
| `neighborhood_damage_rate` | ❌ `np.random.default_rng(42)`, beta draw per spatial hash bucket |
| `foundation_type` | ❌ `np.random.default_rng(42)`, `rng.choice` weighted by construction era and soil type |

The domain priors used in the simulations (regional subsidence rates, soil-type
groundwater norms, foundation-era distributions) are informed by published Dutch
research. The problem is not that the estimators are arbitrary — it is that they
are estimators, not measurements. Calling them "real data" would be wrong.

## The ML approach

This project combines **four data modalities** to produce a per-address risk score:

| Modality | Source | Signal |
|----------|--------|--------|
| Satellite (InSAR) | Sentinel-1 / BodemDalingsKaart | Vertical ground deformation (mm/year) |
| Geospatial | PDOK BAG, TNO DINOloket | Building footprint, year, soil composition |
| Climate | KNMI | Precipitation deficit, drought indices |
| Graph (Phase 3) | Derived | Groundwater-network spatial correlations |

**Model:** Gradient-boosted decision trees (XGBoost) with SHAP explainability for
every prediction — fully aligned with **EU AI Act Article 13** transparency
requirements for automated decisions affecting property.

## Quick start

```bash
# 1. Clone and enter
git clone https://github.com/prakharprakarsh/zakkend-nederland.git
cd zakkend-nederland

# 2. Create environment (Python 3.11 or 3.12)
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt -e ".[dev]"

# 3. Generate synthetic training data
python scripts/train.py

# 4. Launch the API
uvicorn zakkend.api.main:app --reload

# 5. Open the demo
open http://localhost:8000
```

The demo presents **11 numeric sliders** (construction year, soil type, foundation type,
groundwater depth, InSAR deformation rate, etc.). Adjust them and the model returns a
risk class, the four class probabilities, and a SHAP breakdown of the top drivers. The
Leaflet map visualises your click position but does not feed lat/lon into the model.

## Results

All figures from the synthetic 10,000-row run described in [Labels and metrics](#labels-and-metrics).
These measure rule-recovery, not real-world predictive skill.

**Overall:** accuracy 82.9% · macro F1 0.784 · weighted F1 0.827

**Per-class breakdown (2,000-row test set):**

| Class | Precision | Recall | F1 | Support |
|-------|-----------|--------|----|---------|
| low | 72.0% | 54.2% | **61.8%** | 142 |
| moderate | 84.5% | 89.9% | 87.1% | 989 |
| high | 77.5% | 75.9% | 76.7% | 535 |
| critical | 90.2% | 85.6% | 87.9% | 334 |

**`low` is the weakest class** (F1 = 0.618). It is also the smallest class (142 test
samples, 7% of the test set). 65 of those 142 true-`low` buildings are predicted as
`moderate` — the model is systematically conservative, which is arguably the safer
error direction for homeowners but should be acknowledged.

## Known limitations

See [`docs/LIMITATIONS.md`](docs/LIMITATIONS.md) for a full gap analysis. The key
points:

- **Labels are synthetic.** Accuracy measures rule-recovery, not predictive skill.
- **9 of 11 features are simulated** from domain-informed random number generators,
  not measured from instruments or registers.
- **No postcode lookup.** The UI accepts 11 manual numeric inputs; there is no
  geocoder.
- **No probability calibration.** The model outputs raw XGBoost softmax scores.
  `P(critical) = 0.85` does not mean 85% of such buildings will fail.
- **Class imbalance.** The `low` class is underrepresented and has the weakest F1 (0.618).
- **Spatial leakage in the train/test split.** `neighborhood_damage_rate` is assigned
  per spatial hash bucket, so nearby buildings share a feature value across the split.
  The reported accuracy is mildly optimistic as a result.
